6. **Layer placement per start — and a trap in reading it.** The headline number is the same in all
   four logs and means nothing on its own:

   > under `--device none`.**

   It counts the layers the model would place, not where they landed. Placement has to be read from
   the buffer lines, and there the four starts separate cleanly.

   | start | model buffer | KV | compute | graph splits |

   | `e2b-cpu` | CPU_Mapped 3,179.05 + **CPU_REPACK 999.42** | CPU 48.00 + 30.00 | CPU 480.09 | 1 |
   | `9b-cpu` | CPU_Mapped 5,679.25 + **CPU_REPACK 1,705.50** | CPU 256.00 (+ RS 50.25) | CPU 416.07 | 1 |
   | `9b-auto` | **Vulkan0 5,133.63 MiB** + CPU_Mapped 545.62 | Vulkan0 256.00 (+ RS 50.25) | Vulkan0 416.16 (+ host 96.07) | 2 |

   So **yes, llama.cpp used the UHD 620 by itself on both auto starts**, with the fit reporting
   `projected to use 1973 MiB ... vs 7448 MiB of free device memory` for the E2B and

**Predicted vs measured:** the four questions, answered.

**(1) How fast does `gemma4-e2b-it-qat-q4` actually decode here? 5.60 tok/s** on the app's own
argv, **6.83 tok/s** forced to the processor; prefill 19.1 and 22.4 tok/s. This is the first
measurement of this model on this machine and it lands the picker's own recommendation above
the §6.5 crawl gate (`SLOW_PICK_TOKENS_PER_SECOND = 5`, strictly below) on both paths, on a
best-power-efficiency setting. For scale, the class figure the recommendation has been carrying —
**17.0 tok/s** — came from an i7-1185G7 with Iris Xe on the pre-#291 probe basis, and is **3.0×**
what this machine does. It was never a claim about this hardware and should not be read as one.

**(2) Does llama.cpp use the UHD 620 on its own? Yes — 36/36 and 33/33 layers, with real Vulkan0
buffers.** The RTX-3060 pattern reproduces on an integrated part: the picker says `cpu` via the
name gate and the fit puts the model on the device anyway. The gate governs the recommendation and
the tile's basis; it has no influence whatever on placement, because the app passes no `--device`
on rung 1. This is item 22 (j) observed on the integrated class rather than the hybrid one.

**(3) Is auto-offload faster or slower than CPU decode here? Slower — on both models, on both
axes, warm against warm.**

| | auto | cpu | delta |
|---|---|---|---|
| E2B decode | 5.600 | 6.826 | **−18.0 %** |
| E2B prefill | 19.114 | 22.429 | −14.8 % |
| 9B decode | 1.723 | 2.488 | **−30.7 %** |
| 9B prefill | 4.863 | 5.550 | −12.4 % |

**This corrects BUILD_STATE §5 item 21 (e) rather than confirming it.** That entry claims, for this
machine, that auto-offload "gains nothing on pp (56 vs 57 t/s) and LOSES 45 percent on tg (11 vs
19.6)". Measured here:

- **The direction on tg holds.** Auto-offload does lose, and that is the entry's substantive point.
- **The pp claim is wrong in kind.** It reports parity; both models show a real prefill loss,
  12.4 % and 14.8 %.
- **The magnitude on tg does not transfer.** 30.7 % for the 9B and 18.0 % for the E2B, not 45 %.
- **No model here produces those absolute numbers.** 56/57 tok/s prefill and 11/19.6 tok/s decode
  are 3× to 11× anything either model reaches at ctx 8192 behind a 2,000-token prefill. The entry
  names no model and cites no committed evidence; whatever it measured, it was not these two under
  this harness — the shape (high pp, short run) suggests a `llama-bench` pass on something smaller.

Two mechanisms for the loss are visible in the logs rather than inferred. The CPU path gets
**`CPU_REPACK` buffers** (999.42 MiB for the E2B, 1,705.50 MiB for the 9B) — an AVX2 weight repack
the Vulkan path does not receive. And on an integrated GPU the "device memory" is host memory,
so the offload buys no bandwidth while adding an allocation and a second graph split (point 7's RSS
column, plus `graph splits = 2` against 1).

**(4) How far apart are E2B and 9B on identical footing?** On this harness, same ctx, same threads,
same prompt shape, same session:

- **Forced to the processor: 6.826 vs 2.488 = 2.74×.**
- **On the app's own argv (auto): 5.600 vs 1.723 = 3.25×.**

The 2.9 tok/s in the record is not one of these and must not be put in the same table: it is
the app's 64-token `timings` sample of the 9B, against 512 tokens behind a 2,015-token prefill
here. Both are decode-only since #291, and the app's shorter, cache-warm sample reads about 17 %
higher than this harness's 2.488 — the expected direction.

**A cross-check that ties the two bases together anyway.** The app view above persisted
`cpuModelMb: 7384.75` for its 9B start. This session's `9b-cpu` start reports `CPU_Mapped model
buffer size = 5679.25 MiB` and `CPU_REPACK model buffer size = 1705.50 MiB` — **5,679.25 + 1,705.50
= 7,384.75 exactly.** The app's persisted placement is the same processor-path start this harness
reproduces, to the hundredth of a MiB, which confirms the app's own figure was a genuine CPU start
and that the two records describe one configuration.

**What this measurement provides as a basis for the owner calls, stated without a recommendation.**
Per the brief, nothing below argues for a change to `recommendation_rank`, `recommended_ram_gb`,
`USABLE_VRAM_MB` or the name gate; these are the measured facts those decisions would rest on.

- The probe's `freeMb` here is 7,457 MiB. Against §6.6's thresholds the E2B (4,745.6 MiB)
  would clear it and the 9B (8,013.9 MiB) would not — so if the name gate were removed, this
  device would pass the size gate and the card path would star the E2B. Measured, the E2B on this
  device is **18 % slower** than the same model on the processor.
- The §6.6 estimator's conservatism, measured on a third device: `estimateGraphicsNeedMib` puts the
  E2B at 4,745.6 MiB against an actual Vulkan0 footprint of 1,973.8 MiB (2.40× — the Ryzen
  machine measured 2.4× for the same model), and the 9B at 8,013.9 MiB against 5,856.0 MiB
  (1.37×). The 9B's real device need fits the budget while the estimate says it does not.
- The §6.5 sample identity has an oscillation on this machine that the record should note. A check
  run on the 9B measures ≈2.5–2.9 tok/s, below the gate, so the step-down fires and stars the E2B.
  A check then run on the E2B measures ≥5.6, at or above the gate, so no step-down fires and
  the pick returns to the 9B — whose own crawl brings it back. Rule 2's predicate is satisfied in
  both directions (E2B `recommended_ram_gb` 12 ≤ 9B's 16). The E2B figure here is harness-basis;
  the app's shorter sample would read higher still, i.e. further above the gate.
- Question (e) of the protocol — whether an allocation lands in a small BAR heap — has no subject
  on this device, as the preflight already found: one heap, no separate BAR heap.
