WHAT THE NUMBERS SAY
--------------------
1. COLD, on the stick: ~90 ms for the scan (median of 3: 90.3 / 75.6 / 92.2). Reads are
   ~1.6 ms per file open, i.e. per-open LATENCY: 90.6 KiB is ~3.6 ms of bandwidth even at
   25 MB/s. So catalog FILE COUNT drives this, not catalog size — relevant to #311.
   Paid once per session; the model load happening around it moves gigabytes.

2. WARM, which is what a pushed refetch actually pays: end-to-end median 27 ms, of which
   the manifest scan is 18 ms and the settings read + detectSystem() the other ~9 ms.
   82 % of the scan's own warm cost is YAML parse + validateManifest — CPU that no drive
   speed moves. A perfect manifest cache takes 27 ms → ~9 ms.

3. THE TAIL IS NOT THE MANIFESTS. The slowest read of the session (116 ms) had a 15 ms
   scan inside it; the other ~100 ms was the settings read contending with the benchmark's
   own drive probe, which was running at that moment (`drive_benchmark` two lines above it
   in the log). A manifest cache would not have touched that case.

4. THE PERFORMANCE SCREEN IS A MINORITY CALLER. 66 `discover_manifests` in the session
   against 20 `performance_get`: 46 scans came from the other 12 call sites (the start
   gate, the model list, the downloader). Optimising this for the Performance screen alone
   would leave two thirds of the scans untouched.

5. A CORRECTION to the pre-measurement analysis: the app has ONE main window, so the
   "a read per finished chat answer" exposure is smaller than stated — the answer-speed
   push only causes a read while the Performance screen is mounted, and you cannot be
   chatting on another screen at the same time. The realistic repeat drivers are the
   screen's own actions and background events (a model load, a sidecar unloading).

DECISION — owner, 2026-09-09: CLOSE, NO CACHE
-------------------------------------------
Closed on these figures; no cache built. 27 ms median, ~90 ms once per session on a
cold stick, on a screen that is pushed rather than polled, is not a felt delay — and the
available saving is 18 ms of it. Against that, a cache lands on 13 call sites including the
spec §7.4 install gate and the ship-time commercial gate, and reverses the recorded PF-4
ruling ("deliberately NO stateful module cache", build-log 2026-07-10).

NOT MEASURED HERE: a genuinely slow stick. E: reads ~116 MB/s; the #334 SSK stick is
28 MB/s. But the cold cost here is per-open latency and the warm cost is CPU, and neither
scales with sequential speed — a 4x slower medium moves the ~40 ms read component of the
cold sample, not the 27 ms warm median that decides the question.
