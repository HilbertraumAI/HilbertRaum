# CAVEAT on ONE row — `Laufwerk: 1.008,4 MB/s lesen` is CONTAMINATED and must not be cited as this
# drive's media speed. It is an artefact of the session's own preparation, recorded here rather
# than edited out (the report is verbatim, per #414).
#
# This machine's controller is an Intel USB 3.0 xHCI (Gen 1, 5 Gbps ~ 500 MB/s ceiling), so
# 1,008 MB/s cannot come off the media at all. Cause: a pre-flight `Get-FileHash -SHA256` on
# `D:\models\chat\qwen3.5-9b-ud-q4kxl.gguf` (run to check the drive's `require_sha256_match`
# policy before launching) pulled all 5.97 GB into the Windows page cache; the app's read sample
# then hit that warm file. Measured on this drive, same session, 8 MiB sequential reads:
#     cold, 27B at an 11 GB offset never touched ....  407.9 MB/s   <- the real media rate
#     warm, the 9B that had just been hashed ........ 6748.7 MB/s   <- RAM, not the drive
# 1,008.4 sits between the two, i.e. a partly-warm sample.
#
# This is the #392 class (a hash lets a page-cache load sample through the #108 guard), fixed in
# PR #406 by suppressing the load sample for any weight hashed THIS SESSION — a guard that cannot
# see a hash run by an external process, which is what happened here. Not a regression; a blind
# spot worth knowing when preparing a measurement leg.
#
# NOTHING ELSE IN THE REPORT IS AFFECTED. Read speed is an input to neither surface this file is
# evidence for: `liveChatRecommendation` reads the GPU probe + machine RAM + the catalog, and
# `classifyProfile` reads RAM + `gpuUseful` + tok/s. The star and PRO are what they would have
# been on a cold sample.
#

# (ACPI `RHUB#HS11`, then `HS03`, then `HS04` — 43.1-43.7 MB/s across five files, the USB 2.0 High
# Speed ceiling) before being moved to `RHUB#SS07`, where it runs 407.9 MB/s cold. `HS` vs `SS` in
